# Head-to-head benchmark: open-source shadow AI agent discovery tools, including ShadowScan

> **Internal, AI-assisted benchmark. Not an independent review.** The synthetic
> estate, the ground-truth labels, the runner scripts, the scoring rubric and
> this write-up were all produced by an AI assistant working for the
> maintainer, in one session, on 2026-10-08. No second person verified any of
> it. The corpus is author-written, so nothing here estimates field precision,
> recall or calibration for any tool, ShadowScan included. Treat the numbers as
> a reproducible smoke comparison, not as evidence of production performance.

ShadowScan: `d91edb3` on `main` (0.1.1, unreleased), installed from
`requirements.lock` with `--require-hashes`. Python 3.11.15, Go 1.24.7,
Node 22.22.0, Linux x86_64, 4 vCPU, 15 GiB. Outbound HTTPS went through a
policy proxy that allowed PyPI, npm, `proxy.golang.org` and `git clone` from
GitHub but blocked the GitHub API and release downloads. No LLM API keys were
available, so every LLM-assisted analyzer stayed off for every tool. Docker
was present but no tool was run through it.

Why the five were not run: Power Pwn needs a Microsoft tenant or scans the
public internet, neither of which is acceptable here; k8s-aibom and AIOStack
need a Kubernetes cluster (AIOStack also eBPF on the node); Open Shadow AI is
a Docker Compose stack with PostgreSQL and ClickHouse plus an endpoint agent
and a syslog feed; AgentSonar built once `libpcap-dev` was installed and its
`doctor` and `install` commands ran, but a 40-second loopback capture during
synthetic LLM calls recorded no events, and this container's traffic goes
through a local proxy so nothing representative could be produced.

Cisco AI BOM 1.10.0 refuses to start without `--llm-model` (checked in
`aibom/cli.py`); it has no static-only mode, so only MCP Scanner and Skill
Scanner were measured for the Cisco row. Snyk Agent Scan discovers and
inventories without an account, but its analysis step needs `SNYK_TOKEN`, so
its content verdicts are missing too. AI-Infra-Guard's MCP, skill and
agent scanners are LLM-agent driven and were not run; its infrastructure
fingerprinting CLI was.

Reading the ranking honestly: ShadowScan leads because the shared estate is
code, developer-endpoint and export shaped, which is the part of the problem
ShadowScan was built for, and because the rubric rewards breadth. On maturity
it is last among the tested tools. The ordering of the top two does not change
under either re-weighting in section 6, but the gap narrows a lot when
maturity is doubled.

### 2.2 Parity rules

- Same inputs for every tool, documented defaults, no LLM or cloud analyzers.
- Where a tool discovers only from well-known paths, it was run with `HOME`
  pointed at the fake workstation. Where it needs a project directory or an
  explicit config path, it was also run that way, and the union counts.
- Agentic Radar requires a framework name, so all five supported frameworks
  were run against every repository and the union counts.
- Tools that run MCP servers to inspect them were allowed to (Snyk with
  `--dangerously-run-mcp-servers`, Cisco MCP Scanner by default, mcp-audit
  with `--connect`). `npx` servers could sometimes start; `uvx` servers
  never could because `uv` failed TLS through the proxy. The locally planted
  Python server and the HTTP mock always ran.
- ShadowScan's identity, gateway, low-code, SaaS and cloud connectors were
  run on its own bundled offline demo exports only to show they execute. That
  run is reported separately and is not scored against the other tools.

### 2.3 Scoring tiers

- **Found**: the tool's output references the planted file (as a finding
  resource, evidence location, config path, parsed server set, package parsed
  from that manifest, or a graph export that can only come from that file).
  Automated by `harness/score.py`; path-less outputs (agent-bom entities,
  Radar graphs) are mapped by explicit rules in the script.
- **Typed**: the tool labels the artifact as what it is. Manual review of the
  outputs, section 3.2.
- **Content risk**: the tool flags the four malicious items as malicious.
- **Runtime**: fingerprinting of the loopback services.
- **False positive**: an AI-typed finding anchored on a negative file.
  Generic findings (file permissions, VPC flow logs) are not counted.

### 3.4 Runtime surface

AI-Infra-Guard's CLI (`scan --target` and `scan --localscan`, 155
fingerprints, 2169 CVE rules) identified the Ollama mock from its responses
and listed the CVEs for version 0.1.33; `--localscan` also enumerated the
other listening ports. It did not fingerprint the MCP server because it probes
`/` and the endpoint is `/mcp`. No other tested tool observes running services.

The first mock answered unknown paths with a JSON 404 body. AI-Infra-Guard's
`AI-Agent-Config` fingerprint matches any body starting with `{`, without a
status-code check, so it raised a HIGH "agent config file publicly accessible"
finding. Real Ollama answers with a text 404, and the finding disappeared once
the mock did the same. That is a rule weakness worth reporting upstream, not a
false positive against real Ollama.

### 3.5 Surfaces outside the shared estate

Only ShadowScan has connectors for identity providers, LLM gateway logs,
low-code platform APIs, SaaS app installs and cloud accounts. Its bundled
offline demo (`examples/shadowscan.offline.yaml`) completed in 7.8 s with
99 findings: cloud 27, identity 19, SaaS 17, low-code 15, code 11, gateway
10, of which 95 were unmatched by the supplied inventory. That shows the
connectors execute on exports; it does not measure their accuracy, and the
other tools get no score on these surfaces because they have nothing to run.

### 3.6 Negatives and the ambiguous case

- ShadowScan reported one low-risk, confidence 0.5 "LLM usage: Databricks
  Model Serving / Mosaic AI" finding in `ml-training-pipeline`, triggered by
  the `mlflow` requirement. That is a false positive at the LLM-usage level
  and costs it two points in the rubric. The four other negative repositories
  and the two negative files produced nothing; the `agentkeepalive` and
  `https.Agent` traps did not fire. `tests-only-agent` produced a low-risk
  framework-usage finding from the dev requirement and test file, not an
  agent claim.
- agent-bom emits a `project:<name>` entity for every project, including the
  Flask and docs repositories, and an `ai-inventory` entity for the PyTorch
  repository. These are inventory containers, not agent claims, and are not
  counted. It asserted `langchain:LangChain project` for `tests-only-agent`
  from the dev requirement. Its IaC scan raised a flow-log finding on the
  plain VPC file, which is a generic rule and is not counted.
- Agentic Radar's n8n export merged the non-AI weekly-report workflow's nodes
  into the agent graph as tools, an attribution imprecision rather than a
  false positive.
- Snyk, Cisco MCP Scanner, Skill Scanner and mcp-audit produced no findings on
  any negative, because none of them looks at those files.

## 4. Tool notes from the runs

**ShadowScan.** 1.4 to 2.2 s per repository, exit 0 and `complete: true` on
every input. Every finding carries evidence locations. Placeholder-looking
credentials are filtered (documented); realistic-entropy fixtures were flagged
critical and high. It has no `$HOME` auto-walk; pointing `shadowscan code` at
the home directory found every client config and skill. It does not inspect
skill or tool content, by design.

**agent-bom.** Fast (about 1 s per project). Exit code 1 is a "partial scan"
verdict for unpinned versions in `--offline` mode; CI must read the exit-code
contract. Paths in output are redacted to `<path:…>`, which protects privacy
but makes evidence tracing hard. `scan -p <dir>` missed project MCP configs
that `scan -p .` from inside the project found. Terraform agent entities and
framework entities carry no file paths.

**Snyk Agent Scan.** The consent prompt before starting servers reads stdin,
so a non-interactive `inspect` blocked until the timeout; closing stdin fixes
it. With `--dangerously-run-mcp-servers` it ran the planted server and the
HTTP mock and captured both poisoned descriptions. `--json` output was
printed through a console writer that wraps at 80 columns when captured to a
file and had to be unwrapped; `COLUMNS` controls it. Discovery and `inspect` work
without an account. The analysis that turns captured signatures into
findings needs `SNYK_TOKEN`; without it the human-readable mode prints
"To use Agent Scan, set the SNYK_TOKEN environment variable" and `--json`
mode exits 1 with nothing on stdout or stderr, even with `--print-errors`.
So no Snyk verdict on the four malicious items exists in this run, and the
silent JSON exit is a bug worth reporting.

**Cisco MCP Scanner 4.8.5.** Passing `--stdio-timeout` crashes with
`UnboundLocalError: cannot access local variable 'os'`; the environment
variable works. The README's analyzer names (`yara_analyzer`) are rejected;
`yara` is accepted. `--output` is ignored in `config` and `known-configs`
modes and JSON goes to stdout. Servers that fail to start are omitted from
results without an error entry. One `uvx` server crashed the client with
`'Server' object has no attribute 'list_resources'`. YARA caught the SSH-key
poisoning but not the SQL-exfiltration poisoning.

**Cisco Skill Scanner 2.2.0.** About 8 s per repository. Eight findings on the
repository skill, including a YARA prompt-injection rule, the hidden HTML
instruction and the decode-and-execute flow. The best content analysis of the
set without an LLM.

**Cisco AI BOM 1.10.0.** Hard requirement on an LLM model and credentials.
Not measurable here.

**mcp-audit 0.18.2.** Under a second per scan. Its JSON output includes the
raw server config including environment values, so the report file itself
holds the plaintext tokens it found; handle outputs as sensitive. File-mode
findings dominated (the fixtures were 0644). `--connect` needs the optional
`mcp` extra and only speaks SSE for remote servers.

**Agentic Radar 0.14.1.** Needs the framework named up front and exits 1 when
it finds nothing, which is CI-hostile for discovery. CrewAI analysis depends
on the project's own packages being importable. Outputs are HTML plus a graph
JSON without file paths.

**AI-Infra-Guard.** Built with `go build ./cmd/cli/main.go`; the CLI help is
in Chinese. Rule loading takes about 20 s, the scan itself about 1 s. Text
output only from the CLI. The README warns the web platform has no
authentication.

**AgentSonar v1.1.5.** Builds with Go once `libpcap-dev` is present and
`install` sets capabilities. No events on a loopback capture here; untested.

## 6. Rubric

- **Detection (35)**: found-tier recall × 35, minus 2 per AI-typed false
  positive. AI-Infra-Guard scores 3 for being the only tool that identified
  the running service. Untested tools score nothing.
- **Coverage (25)**: nine surfaces, 2.78 each: code repositories, developer
  endpoint configs and skills, container images, cloud accounts, Kubernetes or
  runtime, network service fingerprinting, identity providers, gateway logs,
  low-code and SaaS platform APIs. Full credit when demonstrated here, half

## 7. Limitations

- The estate was written by the same AI assistant that ran the comparison,
  with ShadowScan's documentation in view. The artifacts are generic and
  realistic, but the choice of surfaces favours a breadth-first tool.
- One run per tool, one container, one day. No human looked at any output.
- All LLM-assisted and account-bound analyzers were off. Cisco AI BOM,
  AI-Infra-Guard's MCP and skill scanners and Snyk's analysis would look
  different with keys or a Snyk token.
- The proxy blocked `uvx`, so stdio servers that depend on it never started
  for any tool; this hurt every server-executing scanner equally.
- The found tier is permissive: a path listed as evidence counts. The typed
  tier is a judgement call and is shown in full so it can be disputed.
- Weights are the author's. The raw per-artifact table and the JSON results in
  `head-to-head-2026-10-08/` let anyone re-weight.

## 8. Reproduction

Everything needed is under `archive/reviews/head-to-head-2026-10-08/harness/`.
Set `BENCH` to a scratch directory, run `make_estate.py "$BENCH/estate"`,
`install.sh` (one virtualenv per tool), then the `run_*.sh` scripts; build
AI-Infra-Guard from its repository and AgentSonar with `go install`.
`score.py` reproduces the found tier from the `results/` directory and
`evidence_dump.py` prints the per-tool evidence used for the typed tier.
`truth.json` and `score-found.json` are the labels and the final found-tier
output from this run, with the scratch path replaced by `BENCH_ROOT`.
